## Reachability of 150 MB Target

### Can we hit 150 MB? **NO.**

**Calculation:**
- Purge wheels: 21.1 MB freed
- Purge old PDF versions: ~14 MB freed
- **Total realistic purge:** ~35 MB
- **Remaining:** 2.0 GB − 35 MB ≈ **1.97 GB**
- **Target:** 150 MB
- **Gap:** 1.82 GB of evidence-backed content that cannot be removed without destroying the audit trail

**Why the gap is structural:**
1. **Mesh files alone are 361.7 MB** and are inputs to every simulation run
2. **Solver logs alone are 33.6 MB** and are cited as proof of convergence
3. **Reference papers are 152.4 MB** and document the prior art and methods
4. **The pack overhead (~1.4 GB)** is the git machinery cost; even `git gc` will not reduce this significantly without a shallow clone or mirror strategy

### Alternative strategies to reach smaller targets:

If the absolute target is non-negotiable:

1. **Shallow clone + BFG rewrite** (aggressive): Purge ALL mesh files, all solver logs. Reclaimable: ~395 MB total. Result: ~1.6 GB. Still far from 150 MB. **Cost:** Loss of reproducibility and audit trail.

2. **Git LFS for large files**: Move mesh and log files to external LFS storage. Frees space in .git but moves the problem to a different backend. .git would drop to ~600 MB. **Still above 150 MB.**

3. **Archive + shallow history**: Keep only last 50 commits. Dramatically cuts object count but loses history. Likely achievable for 150 MB. **Cost:** No audit trail, unusual for a lab that publishes results.

### Recommendation:

**Set realistic target to ~1.0–1.5 GB** and accept this as the cost of keeping reproducible research. Execute the 35 MB purge (wheels + old PDFs), use `git gc --aggressive` to pack efficiently, and document that mesh/log preservation is intentional for reproducibility.

If external push requires smaller size, use **Git LFS for mesh and solver logs**, keeping .git lean while preserving data.
