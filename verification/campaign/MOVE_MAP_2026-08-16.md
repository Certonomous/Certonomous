## 6. R3 — Ladder V safety

**Measure, do not assume.** V10's criterion reference had already drifted once,

the form `<path>:<line>-<line>` is treated by this map as broken-on-arrival and
re-derived, never carried forward.**

The classification the mover applies to every reference in an **open** rung:

|---|---|---|

| **LINE-ANCHORED** | `<path>:<n>-<m>` | **re-derived by content search, then re-anchored**; never mechanically shifted |

## 9. The batch plan

**Suite command** (`scripts/lab_check.py` is the only entry point; there is no
CI, no `pytest.ini`, no `conftest.py`):

```bash
python3 /home/ubuntu/Certonomous/scripts/lab_check.py --root /home/ubuntu/Certonomous            # full: ~18 min
python3 /home/ubuntu/Certonomous/scripts/lab_check.py --no-tests --root /home/ubuntu/Certonomous # gates: ~3 min
```

Exit contract is three-valued — **0 PASS, 1 FAIL, 3 UNKNOWN**; a batch is green
only on **0**, and **3 is not green**.

**Standing mechanics for every batch** (each learned from a specific failure):

- **One source per `git mv` invocation.** `git mv` with several sources aborts
  **all** of them if one fails, and a directory holding only gitignored files is
  such a failure. A seven-source move died this way.
- **Never redirect `git mv`'s stderr.** That is how the above failure went
  unseen.
- **The `git mv` commands are the map.** `git status --porcelain` reported
  **19,975 renames** at the reverted attempt, pairing byte-identical OpenFOAM
  case files across unrelated studies. **Git's rename inference is not evidence
  here and is never quoted.**
- **Directories with no tracked file are not moved by `git mv` at all** —
  `solve_registry/` (300 files, 1.51 GB) and `**/surfaces/` were left behind
  before. They are hand-carried with `mv`, per batch, from a written checklist.
- **`git reset --hard` does not undo a `git mv`'s effect on gitignored
  siblings.** The revert stranded ~11 GB of gitignored archives in the new
  directories. **Rollback is therefore never `reset --hard` alone** — see below.
- **786 files under `dafoam/**/work_sail/` are root-owned**, written by the
  DAFoam Docker container. `git mv` on them needs `sudo` or a prior `chown`, and
  discovering that mid-batch is what turns a batch into a partial state.

### 9.0 BATCH 2's CHOICE, RULED 2026-08-17 — option A, and the gate had to be amended with it

`demo-output/website/campaign/MESH_AUDIT_runs/` holds **78 tracked files at
`4d7c195a`, every one a `*.log.checkMesh`, 380,082 bytes tracked and 380,082 on
disk** — precisely the solver-utility class batch 2 untracks. Batch 2 would
therefore take the directory's last tracked file and batch 7's `git mv` of it
would abort, taking every other source in that invocation with it.

**Option A is ruled: batch 2 EXCLUDES those 78 until batch 7 has moved the
tree, then untracks them at the new path.** It keeps the index and the disk in
agreement — the move stays a `git mv` — and holds the carry set at **2 trees /
307 files / 1,510,309,145 bytes**, so G1 keeps its recorded baseline. Option B
(let it go dark, hand-carry it in 7H) grows the carry set to 3 / 385 /
1,510,689,227 by design and would require G1's baseline restated in the same
commit, which is how a gate gets loosened.

**And the plan's own verification defeated that choice, so it was amended in
the same change.** `hand_carry.batch2_survivors()` classified `*.log.checkMesh`
by **file class**, not by what batch 2's list contained, so the stated
condition — *"the goes-dark-after-batch-2 section must read 0 afterwards, not
1"* — read **0 trivially under B** (the tree is already dark, so it is already
in the carry set and the projection reports only the difference) and **1 under
A** (batch 2 spared the files and nothing was going to go dark, but the
projection kept classifying by suffix). **The gate was satisfied by the riskier
option and failed under the safer one.**

`batch2_survivors(tracked, untrack_list)` now tests **membership of batch 2's
actual list**; the exclusion is the named constant `BATCH2_EXCLUSIONS` and is
the default, so the gate's default is the batch's own choice. Executed at
`4d7c195a`, stderr empty on both runs:

| `hand_carry.py derive` | batch 2's list | GOES DARK | carry set |
|---|---:|---:|---|
| option A (ruled, default) | 7,599 paths | **0** | 2 / 307 / 1,510,309,145 |
| `--batch2-option B` | 7,677 paths | **1** (`MESH_AUDIT_runs`) | 2 / 307 / 1,510,309,145 |

`7,677 − 7,599 = 78`. Both directions are pinned by tests and both were
falsified against a planted mutant — the pre-amendment class test reddens the
option-A direction and passes the option-B one, which is the defect reproduced.

**Order rationale.** Batches 1-3 change no path and are individually revertible
with no residue; they retire ~70% of the risk before the first `git mv`. Batch 3
in particular makes batches 4-8 edit *one* module instead of 13 files. **Batch 8
is last** because it is the only one that can take a live surface down, and by
then everything it depends on has been green through seven full suite runs.

**Rollback, stated properly.** For a `git mv` batch: `git reset --hard <sha>`
restores tracked files, **then** the gitignored siblings that followed the
physical directory must be moved back by hand — `git status` will not show them
and `git clean` would delete them. Each move batch therefore carries a written
inverse-`mv` list, produced *before* the batch runs, covering exactly the
directories §9's checklist names as holding gitignored content. A batch without
its inverse list does not start.

**A batch fails** on suite exit 1 **or** 3, on any `git mv` reporting to stderr,
or on any file count not matching the batch's predicted delta. The response is
rollback, not repair-forward: the reverted attempt's cost was a partial state
that nobody could characterise.

### 9.1 THE CONTROL-CORPORA GATE — a gating check, not a note

**No batch from 4 onward may be declared green on a suite result alone.** The
reason is §6.4 item 2, restated here as an executable gate because a note does
not stop anything:

`scripts/use_mention_control_set.json` (115 `demo-output/`-rooted path fields),
`sdk/tests/fixtures/absolute_claims_labelled.json` (66) and
`absolute_claims_labelled_second_instance.json` (92) hold **269 path fields —
306 string occurrences — inside LABELLED CONTROL CORPORA**, re-measured at
`dce05a01` by parsing the JSON rather than grepping it. They are the positive controls that make a
zero from the V10/V16 guards a *measurement* rather than a silence. **Break
them and the guards still pass — and the pass means nothing.** A green suite is
therefore necessary and **not sufficient**: the suite would stay green while
the instruments went blind, which is the precise failure this map exists to
avoid.

**The gate, run after every batch from 4 onward, before the batch is called
green:**

1. **Resolve every path field** in the three corpora against the worktree.
   **Any field that does not resolve fails the batch** — the same
   fail-closed rule repaired into `check_absolutes` at `b0ab070d`, applied to
   the controls themselves.
2. **Re-derive each corpus's positive-control count and compare it to the
   count recorded before the batch.** Equality is the pass condition. A count
   that *fell* is a blinded instrument; a count that *rose* is a corpus that
   absorbed something it should not have.
3. **Fire at least one control both ways** — a planted positive that must be
   found and a negative that must be rejected — because a corpus whose every
   path resolves can still have stopped discriminating.

The repair itself is mechanical: the `"file"` fields take a prefix rewrite
straight from §2's rule table, and the `"sentence"` fields are
**content-anchored, not line-anchored**, so nothing has to be re-derived by
hand. **The gate exists because the repair is easy to do and easy to forget,
and forgetting it is silent.**
