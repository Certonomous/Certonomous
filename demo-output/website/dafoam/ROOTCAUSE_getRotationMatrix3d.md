# Root cause, named to a line: `getRotationMatrix3d`'s degenerate-rotation branch

**Session 2026-07-31, well W5. Nothing in this document has been filed or sent to any upstream project.**

Sections 15–22 of `PROOF.md` established, on two geometries, that `mesh.warpDeriv` disagrees with a
finite difference of the warp it differentiates, by 11% to 207%, with sign flips. What was *not*
established was **which line**. The report's own suggested starting point — a multi-point indexing bug
— was already weakened by A5, whose design variables are plain single-point.

This session names the line, explains the mechanism, tests it with diagnostics designed to fail,
and finds that **the defect is already an open upstream bug that has sat unexplained for five years.**

---

## 1. The line

IDWarp **2.6.2** (the exact version in `dafoam/opt-packages:latest`, digest
`sha256:9d45679d55fd47f5ca7afd99cabb86c7c2729cf2acf34c438eb33af5290f07fc`; the installed
`idwarp/*.py` files are md5-identical to the `v2.6.2` tag of `https://github.com/mdolab/idwarp`,
tag commit `647fd8fc2c06fc61b31cc07a7b63ffd4fbaf65ce`).

### 1.1 The forward warp

`src/warp/warpMesh.F90` computes, per volume node `j`:

```
Xv_j = Xv0_j + numerator_j / denominator_j
```

with the sums built in `src/modules/kd_tree.F90:679–690` (`evalNodeExact`):

```fortran
rr        = r - tp%Xu0(:, i)
LdefoDist = tp%Ldef / sqrt(rr(1)**2 + rr(2)**2 + rr(3)**2 + eps)
Wi        = tp%Ai(i) * (LdefoDist**tp%aExp + tp%alphaToBexp * LdefoDist**tp%bExp)
Si        = tp%Mi(:,1,i)*r(1) + tp%Mi(:,2,i)*r(2) + tp%Mi(:,3,i)*r(3) + tp%bi(:,i) - r(:)
num = num + Wi * Si
den = den + Wi
```

`Wi` is a **constant** with respect to the surface coordinates: the distance uses the frozen
reference surface `Xu0`, and the nodal area `Ai` is assigned only on the initialisation pass
(`kd_tree.F90:1635`, inside `#ifndef USE_TAPENADE`, so Tapenade never sees it). All the
`Xs`-dependence lives in `Mi` (a rotation matrix) and `bi` (a displacement), and `Si` can be
rewritten as

```
Si = Mi·(r − Xu0_i) + (Xu_i − r)
```

so **the rotation acts on the lever arm from the surface node to the volume node.**

### 1.2 Where `Mi` comes from

`src/modules/kd_tree.F90:1639–1640`, inside `computeNodalProperties`:

```fortran
if (useRotations .and. .not. tp%isCorner(i)) then
    call getRotationMatrix3d(tp%normals0(:, i), tp%normals(:, i), tp%Mi(:, :, i))
```

`normals0` is the frozen reference normal; `normals` is recomputed from the current surface
every call. So `Mi = R(n0 → n)`, the rotation carrying the reference normal onto the current one.

### 1.3 The defective construction

`src/utils/vectorUtils.f90:31–103`:

```fortran
real(kind=realType), parameter :: tol = 1.4901161193847656e-08     ! line 44  (= sqrt(eps))
...
call cross_product_3d(v1, v2, axis)
call getMag(axis, axisMag)

! When axisMag is less that sqrt(eps), the acos 'arg' value will be
! exactly one which will give a nan in complex mode.
if (axisMag < tol) then                                            ! line 58   <<< HERE
    angle = zero
    axis  = zero
    axis(1) = one
else
    axis = axis / axisMag                                          ! line 65
    vv1 = v1 / magv1
    vv2 = v2 / magv2
    arg   = min(one, vv1(1)*vv2(1) + vv1(2)*vv2(2) + vv1(3)*vv2(3)) ! line 69
    angle = acos(arg)                                              ! line 70
end if
...
Mi = Mi + sin(angle) * A + (one - cos(angle)) * C                  ! Rodrigues
```

The map `Mi(n0, n)` is perfectly smooth at `n = n0`, with the finite, non-zero derivative
`dMi = [n0 × dn]_×`. But **this particular parameterisation** — normalise the cross product, take
`acos` of the dot product, apply Rodrigues — has a *removable coordinate singularity* there: `axis`
is `0/0` and `d(acos)/d(arg) = −1/sqrt(1−arg²) → ∞`. The `tol` guard exists to stop that becoming a
NaN (the comment says so, and names complex mode as the motivation). It replaces the singularity
with `angle = 0`.

### 1.4 What Tapenade does with the guard

`src/adjoint/outputReverse/vectorUtils_b.f90:123–128`, generated by Tapenade 3.16:

```fortran
CALL POPCONTROL1B(branch)
IF (branch .EQ. 0) THEN            ! the axisMag < tol branch was taken
CALL POPREAL8ARRAY(axis, realtype*3/8)
magv2b = 0.0_8
axisb = 0.0_8
axismagb = 0.0_8
ELSE
   ...
```

When the guard fires, the reverse sweep **zeroes every adjoint on the path back to `v2`**. The
subsequent `GETMAG_B` and `CROSS_PRODUCT_3D_B` calls therefore add nothing, and

```
dMi/dnormals = 0, exactly.
```

Tapenade is not at fault. It differentiated the branch that was taken, correctly. The defect is that
the branch that was taken is a **constant** in a place where the true function has a non-zero
first-order term.

### 1.5 Why the guard *always* fires at a gradient evaluation

`getMag` regularises: `mag = sqrt(v(1)**2 + v(2)**2 + v(3)**2 + 1e-30)`. At an undeformed baseline
`normals == normals0` bit-for-bit (same code, same inputs), so `axis = n0 × n = 0` and
`axisMag = sqrt(1e-30) = 1e-15 < 1.4901e-08`. **Branch 0, guaranteed.**

A `check_totals`, a first design iteration, and every one of this lab's gradient probes are
evaluated at exactly that state. Meanwhile the finite difference perturbs the surface by `h`, which
tilts the adjacent faces by `θ ~ h/L`, far above `1.49e-08`, so **the FD sees a first-order rotation
term that the AD has set identically to zero.** That difference *is* the 11%–207% gap.

### 1.6 The second regime

Away from the baseline (`axisMag` just above `tol`), the guard does not fire and the derivative *is*
computed — through `argb = -(angleb/SQRT(1.0-arg**2))` with `arg → 1`. `1 − arg ≈ θ²/2` is formed by
catastrophic cancellation. So there are two failure regimes from one parameterisation: **silently
zero** at `n ≈ n0`, and **ill-conditioned** just above the threshold. Section 4.3 below measures the
second one directly on ONERA M6.

### 1.7 The fix that would remove both

The singularity-free form of "rotation taking `a` to `b`" avoids `acos` and the normalisation
entirely:

```
v = a × b ,  c = a·b ,  R = I + [v]_× + [v]_×² / (1 + c)
```

`R` is a polynomial in `v` with the smooth coefficient `1/(1+c)`; at `a = b` it gives `I` with the
correct derivative, needs no threshold, and cannot NaN except at `c = −1` (exact reversal), which is
a genuine singularity of the problem rather than of the parameterisation. This is offered as an
analysis, not as a patch: nothing has been submitted anywhere.

### 2.2 Why it stayed invisible upstream

Three independent mechanisms, each verified against primary source:

1. **The assertion is missing.** `tests/test_USMesh.py:86` calls
   `mesh.verifyWarpDeriv(dXv_warp, solverVec=False, dofStart=0, dofEnd=5)` and discards the result.
   Nothing is asserted on it. This is exactly what issue #57 says.
2. **The only thing actually asserted is blind to this error by construction.** The regression check
   is `handler.root_add_val(f"{test_name} - Sum of dxs:", val, tol=1e-8)` — the *sum* of `dXs`.
   Section 4.2 shows that across five meshes the rotation term contributes **exactly zero to that
   sum** while changing `||dXs||` by factors of 5 to 34. A stored-reference check on the sum cannot
   see it.
3. **The dot-product test cannot detect it either, and is not run.** `examples/structured/dotprod.py`
   is in `examples/`, not `tests/`. And a dot-product test only proves forward-AD and reverse-AD are
   mutual transposes; if both linearise a *different function* than `warpMesh`, they do so
   identically and the dot product is still zero.
4. **Upstream's own verification tool defaults to a random seed.** `UnstructuredMesh.py:460`:
   `def verifyWarpDeriv(self, dXv=None, ..., randomSeed=314)`, and `if dXv is None: np.random.seed(randomSeed)`.
   The random seed is the one seed under which this lab already knows the defect hides (PROOF.md §17).

## 3. What would have falsified the mechanism

Stated before the runs, so the diagnostics are not retrofitted:

| # | prediction | what would have refuted it |
|---|---|---|
| P1 | `warpDeriv`'s output is **bit-identical** with `useRotations` on and off, because the rotation branch contributes exactly zero | any change in `||dXs||`, `sum(dXs)` or `max|dXs|` |
| P2 | With `useRotations=False` the warp becomes exactly linear in `Xs` (`Wi` constant, `Si = Xu_i − Xu0_i`), so FD must equal AN to roundoff — not merely "improve" | error stalling at a few percent, or staying at 100%+ |
| P3 | The primal baseline `Xv` is identical on/off, because `Mi = I` either way at `n = n0` | any change in `||Xv0||` |
| P4 | Forcing `Mi = I` through the **corner** path instead must give the same collapse | errors surviving |
| P5 | `evalMode="exact"` (no KD-tree truncation at all) must **not** help | errors collapsing, which would mean the truncation hypothesis, not ours |
| P6 | Adjoint matrix reordering (`rcm` vs `natural`) must not move the result at all, `warpDeriv` being purely geometric | any material change |
| P7 | A surface direction that rotates no normals must come out clean **even with rotations on** | large error on a rotation-free direction |

Fingerprints, both runs: `sum(dXs)=3.229531100101105e+04`, `||dXs||=4.572421801411781e+02`,

**Why DOFs 0 and 3 and not 1, 2, 4, 5.** DOF index = `3·node + component`. `inflate_cube` scales an
axis-aligned block by (1.1, 1.2, 1.3), which leaves every face normal *exactly* unchanged — hence the
guard fires even at the deformed state. Perturbing a node **along** its face normal (the `x`
components, DOFs 0 and 3, `OrigVal = 1.10000`) tilts the adjacent faces at first order and switches
the rotation term on. Perturbing it **in** the face plane (`y`, `z`) does not tilt them at first
order. That is P7, appearing unbidden inside upstream's own five-year-old data.

**Adversarial check — is the FD real, or is it FD noise?** The issue's author raised exactly this
doubt. Step-size study on the two failing DOFs:

|---|---|---|
| 1e-4 | −115.875670601 | −94.3794920109 |
| 1e-5 | −115.875777546 | −94.3795512483 |
| 1e-6 | −115.875789153 | −94.3795845788 |
| 1e-7 | −115.859319381 | −94.3687867546 |
| 1e-8 | −114.229767757 | −92.6558174640 |

Stable to 6 significant figures across three decades, with subtractive roundoff appearing only at

answered.

derivative vector by a factor of 34.**

`onera_m6` with rotations on shows 1.02%, 1.26%, 0.39%, then decaying monotonically to 0.0036% down
the DOF list — small but far above the 1e-6% floor the same mesh reaches with rotations off. This is
§1.6's ill-conditioned regime: rotation angles just above threshold, `1 − arg²` formed by
cancellation. Recorded as a measurement, not as a second confirmed mechanism.

### 4.5 The independent code path (P4)

`cornerAngle` sets `threshold = cos(cornerAngle·π/180)` and flags a node a corner when
`|faceNormal · normals0| < threshold` (`kd_tree.F90:1682–1712`), and corners get `Mi = I` by literal
assignment — a different branch from `useRotations`.

**A first attempt got this backwards and is recorded rather than hidden.** `D2` used
`cornerAngle=180`, which gives `threshold = −1`, so `|dp| < −1` is never true and **no** node is a
corner — the opposite of the intent. It *disables* corner-rotation-zeroing. The errors persisted
(idx8 161.6%, idx17 116.9%) and the FD moved *further* from AN (idx8 FD `7.879e-01` → `1.369e+00`),
i.e. more rotating nodes, a larger discarded term. Consistent with the mechanism, but not the test
that was intended.

`D2b`, `cornerAngle=0.001` (threshold ≈ 1, so essentially every node is a corner): **all six
components 0.0000, AN fingerprint bit-identical to every other run**
(`||dXs||=1.495168856286067e+03`). P4 confirmed through the independent path.

### 4.6 The competing hypothesis, killed (P5)

The KD-tree fast-sum truncation is a real approximation (`errTol=5e-4` by default) and the descent
criterion is evaluated separately in the primal and the reverse pass, so "the two passes truncate
differently" was a live alternative explanation. `D3`, `evalMode="exact"` — no truncation at all,
with rotations on:

| idx | err, evalMode=fast | err, evalMode=exact |
|---|---|---|
| 8 | 207.0% FLIP | **204.7% FLIP** |
| 17 | 121.6% FLIP | **123.8% FLIP** |
| 3 | 177.8% | 198.6% |

**Unchanged. The truncation hypothesis is refuted.** It is independently refuted by §4.4: with
rotations off the errors go to zero while `evalMode` is still the default `fast`.

### 4.7 The reordering question (P6)

Katie's standing question: the failing scripts use `jacMatReOrdering: rcm` where the one working
tutorial uses `natural`, and it had never been varied. Note first that `UBend_Channel` ships
`natural` and fails anyway. Varied explicitly (`D5a`/`D5b`):

### 4.9 Capstone: pre-deform the baseline so the guard does *not* fire

The sharpest consequence of §4.2's narrowing is a prediction about this lab's own case, not about
IDWarp's test meshes. If the failure really is the degenerate branch, then moving the U-bend off its
undeformed baseline — so the current normals no longer coincide with the reference normals — should
make the guard stop firing, at which point `warpDeriv` must (a) *become* sensitive to `useRotations`,
and (b) get dramatically more accurate. If instead the rotation term were mis-differentiated
generally, pre-deforming would change nothing.

## 5. Verdict

**Sequel, 2026-08-01: the root cause below is now CONFIRMED BY REPAIR.** The corrected
degenerate-branch derivative (`v2b += (axial(mib - mib^T) x v1)/(magv1 magv2)`, four lines in the
generated reverse file) collapses every error in this document to FD-truncation level with
rotations ON — issue #57's 210%/213% to 8.6e-06%/3.4e-05%, A5's 207%/122% flips to 3e-06/7e-06,
A1's 634% flip to 5.5e-04% — with the primal bit-identical and the live branch untouched.
Derivation, patch, unit experiment, and all acceptance runs: `PATCH_getRotationMatrix3d.md`,
`rotation_branch/idwarp_v2.6.2_degenerate_branch_fix.patch`, `rotation_branch/patched/`.

`mesh.warpDeriv` returns a derivative from which the surface-normal-rotation term is **exactly
absent** whenever the current surface normals coincide with the reference normals — which is
precisely the state at which every adjoint gradient is evaluated. The term is discarded at
`src/utils/vectorUtils.f90:58` by a `sqrt(eps)` guard whose Tapenade reverse
(`src/adjoint/outputReverse/vectorUtils_b.f90:123–128`) zeroes the entire adjoint path. Setting
`useRotations=False` makes the warp exactly linear and the analytic derivative exact — and leaves
`warpDeriv`'s output **bit-identical**, which is the proof that the term was never in it.

Confirmed on **six** geometries: A1 NACA0012, A5 UBend_Channel, and IDWarp's own `symm_block`,
`o_mesh`, `co_mesh`, `sym_mesh` and `onera_m6`. Explains an **open upstream bug from 2021** that has
never been answered, and explains why upstream's CI cannot see it.

### 5.1 Actionable workaround, with its cost stated

**`useRotations: False` in `meshOptions` restores gradient consistency**, on this evidence, to
roundoff. It is not free: upstream documents rotation interpolation as what *"will help preserve
boundary layer orthogonality"* under large orientation changes, so mesh quality under large
deformation is the price. That trade has **not** been measured by this lab and no optimisation has
been re-run under it. Recommending it as a default would be premature; that measurement is docket
item `w5-rotations-off-mesh-quality-price`.

### 5.2 What is still open

- The AIAA paper (§2.3) is unread. The "undocumented" claim rests on code, docs and release notes only.
- ~~§1.6's second regime (ill-conditioned, just above threshold) is measured on ONERA M6 at ~1%
  but not isolated to a line the way the first regime is.~~ **CLOSED 2026-08-02, see §7.** The
  error-vs-angle curve was measured 2026-08-01 (§6.4); the cause was *tested* 2026-08-02 and is

  `vectorUtils_b.f90:133`'s cancellation together -- each alone buys 1.0x-1.6x, the pair buys

## 7. The second regime's cause, tested rather than asserted, 2026-08-02

§6.4 measured an error-vs-angle curve and named `vectorUtils_b.f90:133`,
`argb = -(angleb/SQRT(1.0-arg**2))`, as the carrier, on the reasoning that `1 - arg^2 ~ theta^2` is
formed by catastrophic cancellation. **That was a location plus an asserted mechanism.** This
section repairs each candidate line in isolation and measures what each repair buys. Script and
log: `independent_check/regime2_mechanism.{py,log}`, run 2026-08-02T08:27:46Z. Zero compute --
numpy only, no IDWarp, no DAFoam, no solver.

**7.1 The discriminator is free.** `sqrt(1 - arg^2)` is `sin(angle)`, and `sin(angle)` is
`axisMag/(magv1*magv2)` -- and `axisMag` is *already computed two lines earlier in the primal*,
because it is what normalises `axis`. So the substitute costs nothing and, measured against exact
`sin(theta)`, is accurate to **0 to 5.0e-15 relative across the whole range** (Part C), while the
shipped `1 - arg^2` is wrong by **11.0% at `theta = 2e-08`** and by 2.3% at 5e-08 (Part B). The
cancellation §6.4 named is real, severe, and exactly where it was said to be.

**7.2 And repairing it does almost nothing.** Four variants of the reverse routine, differing only
in the marked lines, against the true derivative of the smooth map:

| `theta` | V0 shipped | V1 denominator only | V1b angle only | V2 both | V3 §1.7 singularity-free |
|---|---|---|---|---|---|
| 1e-06 | 6.658e-05 | 5.561e-05 | 3.661e-05 | **1.974e-10** | 1.538e-12 |
| 1e-07 | 3.998e-04 | 3.339e-04 | 2.199e-04 | **7.221e-10** | 1.710e-12 |
| 5e-08 | **1.161e-02** | 9.663e-03 | 6.436e-03 | **3.083e-09** | 2.229e-12 |
| 3e-08 | 6.603e-03 | 5.504e-03 | 3.647e-03 | **1.077e-09** | 1.041e-12 |
| 2e-08 | **5.286e-02** | 4.483e-02 | 2.801e-02 | **4.844e-09** | 1.068e-12 |
| <=1.49e-08 (guard) | 1.0 | 1.0 | 1.0 | 1.0 | **9.3e-13** |

V1 is the one-line fix §6.4's attribution points at. It buys **1.0x to 1.6x**. Over 200 random
`(v1, mib, tilt-axis)` draws per angle it buys 1.0x to 1.6x again, while **V2 buys 2.1e+03x to
3.7e+07x** (Part D). Fixing only the denominator is indistinguishable from doing nothing.

**7.3 So the carrier is the angle, in the PRIMAL, and the cause spans two lines not one.** The
dominant term is `angle = acos(arg)` at `vectorUtils.f90:69-70`: `arg = 1 - theta^2/2` loses the
information at `theta ~ sqrt(eps)` before `acos` is ever called, so `angle` itself carries relative
error `~eps/theta^2` and the reverse inherits it through `sin(angle)`, `cos(angle)` and `angleb`.
Line 133's cancellation is a second, comparable term. **Neither is sufficient alone and the two do
not add** -- repairing either leaves the other at nearly full size, which is why each single-line
repair reads as a null result. Only `angle = atan2(axisMag/(magv1*magv2), arg)` *together with*
`sqrt(1-arg^2) -> axisMag/(magv1*magv2)` removes the regime.

**7.4 Which answers the item's actual question: two regimes, and they need different fixes.** The
shipped patch (`idwarp_v2.6.2_degenerate_branch_fix.patch`) is deliberately **primal-bit-identical**
-- that is one of its acceptance criteria and it is why it is safe. A regime-2 repair *cannot* be:
it changes `angle` in the forward warp. Measured (Part E), `Mi` moves by **1 ulp at `theta = 1`,
2.7e-15 at 1e-01, and 2.0e-08 at `theta = 2e-08`** -- and at that angle the whole rotation
contribution is itself only O(2e-08), so the forward warp's rotation term is 100% uncertain there.
The primal is not being perturbed by the fix; it was already wrong and the fix is what makes it
right. But it does mean **a full fix cannot claim primal-invariance, and any regime-2 patch must be
re-graded on the primal as well as the gradient.**

**7.5 What this does to `w5-idwarp-singularity-free-rotation-patch`.** §1.7's reparameterisation
(V3) is now measured, independently and in double precision, at **6.3e-13 to 2.2e-12 across every
angle tested including inside the guard ball**, where every acos-based variant reads exactly 1.0.
It is the only single change that covers both regimes, and it needs no threshold. That item's
premise is strengthened, not weakened, by this section.

**7.6 Stated against ourselves.** This is a numerical study of a faithful transcription, not a run
of IDWarp. It says which lines carry the error in the algorithm as written; it does **not** measure
what tilt angles a real deformed mesh actually visits. ONERA M6's 1.02%-1.26% is consistent with
`theta ~ 5e-08` off this curve, but that inversion is an inference, and no direct measurement of
normal-tilt-angle distributions on a real case exists here.
