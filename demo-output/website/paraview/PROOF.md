# ParaView Headless Installation Proof

## Installation Route

Official ParaView headless tarball (EGL build) from paraview.org.

Initial attempt: ParaView 5.11.2 via apt (sudo apt-get install -y paraview python3-paraview) failed. The apt build lacked proper headless rendering support and crashed with segmentation faults when attempting offscreen rendering.

Final solution: ParaView 5.13.3 EGL-MPI build (official headless)
- Downloaded: ParaView-5.13.3-egl-MPI-Linux-Python3.10-x86_64.tar.gz from https://www.paraview.org/files/v5.13/
- Extracted to: /opt/ParaView-5.13.3-egl-MPI-Linux-Python3.10-x86_64
- Symlink: /opt/paraview points to full installation path

## Exact Version

ParaView 5.13.3 (confirmed via: pvbatch --version)

## Critical Finding: pvbatch vs pvpython

The standalone pvpython command failed with GLEW initialization errors even with EGL build. The dedicated batch tool pvbatch succeeded immediately on first attempt. Use pvbatch for all headless rendering, not pvpython.

## Headless Environment Setup

Copy-pasteable environment block for headless ParaView invocation:

```bash
export PATH="/opt/paraview/bin:$PATH"
export LD_LIBRARY_PATH="/opt/paraview/lib:$LD_LIBRARY_PATH"
export DISPLAY=""
/opt/paraview/bin/pvbatch your_script.py
```

No additional OSMesa or EGL-specific environment variables needed. The EGL build handles headless rendering natively.

### CHECK 1: PROVENANCE OF naca4412_wing_field.json

The JSON was generated by extract_and_paint() in workflows/geometry_study.py (line 1199-1227).

Code path (chief_engineer/field_render.py line 324-377):

1. Executes: openfoam2606 foamToVTK -latestTime -surfaceFields
2. Extracts VTP boundary field files from OpenFOAM case
3. Reads per-point or per-cell pressure values from VTP with no synthesis
4. No density multiplication or other transformations before JSON

Code excerpt (field_render.py lines 91-113):
    # Pressure: prefer per-point (smooth), fall back to per-cell.
    values_by_vertex: list[float] | None = None
    point_section = _POINTDATA.search(text)
    if point_section:
        values_by_vertex = _named(point_section.group(0), field, header_bytes)

    face_values: list[float] = []
    if values_by_vertex:
        for face in faces:
            face_values.append(sum(values_by_vertex[i] for i in face) / 3.0)
    else:
        cell_section = _CELLDATA.search(text)
        per_cell = _named(cell_section.group(0), field, header_bytes) if cell_section else None
        if per_cell:
            expanded: list[float] = []
            start = 0
            for poly_index, end in enumerate(offsets):
                tris = max(1, (end - start) - 2)
                expanded.extend([per_cell[poly_index]] * tris)
                start = end
            face_values = expanded[:len(faces)]

    return vertices, faces, face_values

Conclusion: The JSON contains raw solver output from foamToVTK. Pressure values are extracted directly from OpenFOAM's boundary field output without synthesis or resampling.

### CHECK 2: UNITS AND PHYSICS VERIFICATION

CRITICAL FINDING: The pressure values are KINEMATIC PRESSURE (m^2/s^2), NOT absolute pressure (Pa).

Evidence:
- simpleFoam solves for p/rho (kinematic pressure, per OpenFOAM documentation)
- transportProperties file: nu = 1.5e-05 m^2/s (kinematic viscosity only, no density)
- controlDict: rhoInf = 1.225 kg/m^3 and magUInf = 15 m/s specified for coefficient calculation
- simpleFoam is incompressible solver; does not multiply by density
- foamToVTK outputs solver fields without unit conversion
- field_render.py line 268 applies no density multiplication

LABELING ERROR IN PREVIOUS REPORT:
Previously stated "Field minimum: -69.74793752034505 Pa" is WRONG.
Correct statement: "Field minimum: -69.74793752034505 m^2/s^2 (kinematic pressure)"

PRESSURE COEFFICIENT CALCULATION AND PHYSICAL ANOMALY:

Case parameters from controlDict and transportProperties:
- magUInf = 15.0 m/s (freestream velocity)
- rhoInf = 1.225 kg/m^3
- lRef = 1.0003 m (wing chord, reference length)
- nu = 1.5e-05 m^2/s (kinematic viscosity)

Verification:
Reynolds number: Re = (U * L) / nu = (15 * 1.0003) / 1.5e-05 = 1.00e+06 (matches brief statement)

Dynamic pressure (kinematic): q = 0.5 * U^2 = 0.5 * 15^2 = 112.5 m^2/s^2

Pressure coefficient (for kinematic pressure): Cp = p / (0.5 * U^2) = p / 112.5

Using the clipped percentile values from JSON (2nd/98th percentile):
- p_min = -69.7 m^2/s^2  yields Cp_min = -69.7 / 112.5 = -0.6189
- p_max = 26.8 m^2/s^2   yields Cp_max = 26.8 / 112.5 = 0.2382

PHYSICAL ANOMALY IDENTIFIED:

For a stagnation point, Cp must equal 1.0 (flow comes to rest, pressure rises to maximum).
A wing at Re 1e6 must have a stagnation point at or very near the leading edge.

Measured Cp_max = 0.2382 is far below expected 1.0.
Shortfall: 1.0 - 0.2382 = 0.7618 (76.2% below expected)
This is a factor of 4.2x error: 1.0 / 0.2382 = 4.2

CORRECTION (2026-07-26 investigation, see below): an earlier version of this
file compared the extracted Cp range to "published NACA 4412 aerodynamics ...
Cp over lower surface suction: -6 to -8". That number is wrong and has been
removed. Cp values of -6 to -8 correspond to a very high-lift or high-incidence
condition (or a much higher local velocity ratio than a NACA 4412 near
alpha 0 ever produces). For a NACA 4412 at low incidence, 2D thin-aerofoil and
published wind-tunnel polars put the suction peak on the order of -1 to -2;
a finite, low-aspect-ratio wing is milder still because the tip relieves the
spanwise loading: this case has planform area Aref = 3.0009 m^2 and chord
lRef = 1.0003 m, so span b = Aref / lRef = 3.00 m and AR = b^2 / Aref = 3.0.
There is no citation for "-6 to -8" anywhere in this repository; it should
never have been stated as sourced fact.

The properly sourced comparison is the RAW solver field for this exact case,
read directly off the OpenFOAM output, bypassing the JSON and the paint
pipeline entirely:

- Source: `~/certonomous-runs/.solve-cache/naca4412_wing-c337334-i300/120/p`
  (the converged time-120 internal field, cached from the same solve that
  produced this study) mapped through
  `~/certonomous-runs/.mesh-cache/naca4412_wing/polyMesh/{owner,boundary}`
  to the `body` patch's 32,970 boundary faces (`zeroGradient`, so each wall
  face value equals its owner cell's internal `p`, per OpenFOAM's own
  boundary evaluation - no interpolation invented here).
- Raw wall p (kinematic, m^2/s^2): min = -119.63, max = 100.09.
- Raw wall Cp (q = 112.5 m^2/s^2): **Cp_min = -1.06, Cp_max = 0.89.**

That is a physically coherent NACA 4412 near-stagnation result (Cp_max
approaching 1, as it must at a stagnation point; Cp_min around -1, consistent
with a mild suction peak on a low-AR wing at a small positive incidence
relative to the zero-lift line). It is NOT close to the JSON's reported
Cp range of -0.62 to +0.24.

CONCLUSION FOR CHECK 2 (updated):

(A) UNITS ARE KINEMATIC m^2/s^2, NOT Pa. This is a factual labeling error,
    corrected above.

(B) Cp ANALYSIS REVEALS A REAL EXTRACTION BUG, NOT A SOLVE PROBLEM: the raw
    wall field (Cp_max 0.89, Cp_min -1.06) is physically sound. The published
    JSON's field (Cp_max 0.24, Cp_min -0.62) is not the raw field - it is a
    smoothed-and-then-percentile-clipped derivative of it.

(C) CAUSE, confirmed by reproducing `foamToVTK -latestTime -surfaceFields`
    from the cached mesh + solved fields and running the production
    `sdk/chief_engineer/field_render.py` code against the result:
    1) `foamToVTK`'s own cell-to-vertex interpolation mildly smooths the peak
       (Cp_max 0.89 -> 0.86 at the nodal/point-data stage).
    2) The wing's fan-triangulated surface is 66,966 triangles, above the
       `_package_painted` decimation threshold (`max_faces=30000` in
       `load_field_surface`, `field_render.py` line 118), so it takes the
       vertex-clustering decimation branch (lines 172-227): each display
       face is the arithmetic mean of every source face whose corners
       collapsed into the same cluster cell (lines 218-227). Because the
       stagnation peak is concentrated in a small number of faces near the
       leading edge, clustering averages it with its cooler neighbours:
       Cp_max drops from 0.85 (pre-decimation face value) to 0.72
       (post-decimation).
    3) `_attach_field` (lines 245-270) then clips to the 2nd/98th percentile
       of the *decimated* face values and reports that clipped range as
       `field.min`/`field.max` - i.e. as if it were the physical range of the
       field, not a display convenience. That step alone takes Cp_max from
       0.72 to 0.32 and is the single largest cut (the stagnation region is a
       sharp, thin spike, so trimming the top 2% of faces removes most of it;
       the broader suction trough loses proportionally less at the bottom).
    Reproduction numbers (this investigation, `/tmp/scratch_investigation`):
    raw wall Cp_max 0.89 -> nodal (point-data) Cp_max 0.86 -> per-face
    (fan-triangulated) Cp_max 0.85 -> post-decimation Cp_max 0.72 ->
    post-percentile-clip Cp_max 0.32 (published JSON: 0.24, same order,
    small remaining gap likely from run-to-run float32/ordering differences
    in `foamToVTK`, not from a different mechanism).

The rendered image is not synthetic and not from the wrong surface - it is
the correct body, painted with a field whose reported min/max have been
quietly redefined by two independent smoothing/clipping steps in the
extraction pipeline. This cannot be published as "the pressure range on the
wing" without saying so, and the fix (whether to report the raw range
alongside the display range, or something else) is left to the pipeline
owner - this file only documents the mechanism.

### Rendering Method

Since the OpenFOAM case directory lacked the mesh polyMesh (only initial conditions and geometry definition), the actual field data was loaded from the processed JSON file which contains both geometry and solution fields. A VTK polydata surface mesh was constructed from the JSON geometry, pressure values were attached as cell data, and the mesh was rendered using ParaView batch mode with scalar coloring by pressure.

Script approach:
1. Load JSON with vertices, triangular faces, and pressure field values
2. Construct vtkPolyData mesh in memory
3. Attach pressure field as cell scalars
4. Export to temporary VTK file
5. Load in ParaView via OpenDataFile()
6. Render with pressure scalar coloring
7. Save screenshot at 800x600
