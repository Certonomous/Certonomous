### 3.1 C5 — the repaired token scan, and the defect it removes

SO-1a's grader carries at `so1a_grade.py:122-125` the token `"Floating point exception"` applied by `fatal_tokens_in(text)` as a **whole-file substring test** (`return [t for t in FATAL_TOKENS if t in text]`). OpenFOAM's standard startup banner is `trapFpe: Floating point exception trapping enabled (FOAM_SIGFPE).` — **a notice that the solver is PROTECTED against the very failure the token exists to detect**. SO-1a's own run put that line at `MESH/checkMesh.log:18`; its grader refused and published `NOT A RESULT` **with zero gates evaluated** on a run whose five arms were all `rc = 0`, and **the refusal named the arm log, a file this lane verified contains the token zero times** (`X-S_20260828T021855Z_1711422.log`, 690 lines).

**The repaired logic is PORTED from `curriculum_SO1c/so1c_grade.py` @ `42c7c8c3`, which is the only place in this family where it is correct, and is not re-derived from the ancestor.** The token is **NOT deleted** — deleting it blinds C5 to a real SIGFPE, and a missed crash is laundered into a result while a false hit costs a re-read. Instead:

* `fatal_token_sites()` scans **PER FILE and LINE BY LINE**, so a benign banner on line 18 can never suppress — and never impersonate — a real crash on line 400, and every refusal names the **file and the line**.
* `benign_reason()` is applied **per line** with **exactly one** exclusion, `^\s*trapFpe:\s`.
* **Every exclusion is COUNTED AND NAMED on the PASS record.** A suppression a reader cannot see is the same defect wearing the other hat.
* **`Foam::sigFpe::sigHandler` is added as an extra POSITIVE token** — the one string OpenFOAM emits only when the handler has actually FIRED — **without** the `^` line anchor `sdk/chief_engineer/head_engineer.py:188` puts on it, because at np > 1 the realistic report is OpenMPI's `exited on signal 8 (Floating point exception)`, which is not line-initial.

**What "the bare token is not present" means here, precisely, because the phrase can be read two ways.** The **string** is present and must be: it is a registered token. What is gone is the **defect** — the whole-file substring scan. ### 3.2 §2a identity test, answered for the three gates that carry this item

* **`G5g`: what would make it FAIL?** A graded pair whose FD estimate of the constraint derivative differs from the adjoint by more than 5 %, or in sign. **Could a wrong treatment still PASS it?** Yes, in one way we can name: a defect that scales BOTH the adjoint and the FD estimate identically — a wrong normalisation inside pyGeo's `scaled=True` — cancels in the ratio. That is why **`G-CV` separately bands the constraint VALUES** (P2/P3): a mis-scaled constraint moves the baseline off 1.0 even when the ratio agrees.
* **`G-STRUCT`: what would make it FAIL?** Any non-zero `d(constraint)/d(patchV)` on either side. **Could a wrong treatment still pass it?** Yes, and it is the obvious one: a reader that returns zeros because it is reading the wrong key, the wrong slice, or an empty list. That is exactly why the gate is not composed until the planted control fires and why the comparator **requires G-STRUCT to flip to `GATE FAIL` on a copy of the real artefact with `PLANT` added to one `patchV` entry** (U57). A gate that passes on a zero and has never been shown reading a violation is not evidence.
* **`G-TB`: what would make it FAIL?** A cyclically shifted pairing agreeing within a factor of ten of the true pairing. **Could a wrong treatment still pass it?** Yes: a Jacobian whose four shape-component entries are genuinely near-identical for physical reasons would collapse the ratio and read `GATE FAIL` when nothing is wrong. That failure mode is registered as **a withdrawal to `NOT A RESULT`, never a `GATE FAIL` on the physics**, and the per-constraint numbers are printed so the reader can see which constraint did it.
