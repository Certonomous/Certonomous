  1. Test the address, tonight, not in the morning

    Open a browser on your laptop and go to the control room. If it loads, you need no commands at all on the laptop. Skip to step 4.

    http://16.58.201.228:8765

    The static site is the same address on the other port, and this page lives there too:

    http://16.58.201.228:8080/shoot.html

    If the page hangs rather than erroring, the two ports were most likely never opened on the instance. That is the single most likely thing to go wrong, which is why it is worth thirty seconds the night before. The fix is step 2, and step 2 works either way.

  2. If it does not load: the SSH tunnel

    This works whether or not the firewall is open, and it is the safer option anyway: the demo then runs on localhost, nothing is exposed publicly, and a changed address does not matter. Leave the window open for the whole shoot.

    Git Bashon your laptop · preferred
    ssh -i ~/.ssh/your-key.pem -L 8765:localhost:8765 -L 8080:localhost:8080 ubuntu@16.58.201.228
    PowerShellon your laptop · same command, Windows-style key path
    ssh -i C:\Users\<you>\.ssh\your-key.pem -L 8765:localhost:8765 -L 8080:localhost:8080 ubuntu@16.58.201.228

    With the tunnel open, the browser addresses become:

    http://localhost:8765     http://localhost:8080/shoot.html

    The one Windows gotcha. If SSH refuses the key with "UNPROTECTED PRIVATE KEY FILE" or "bad permissions", the key file is readable by too many users. Fix it in whichever shell you are already in, then run the tunnel command again.
    Git Bashon your laptop · key permissions
    chmod 600 ~/.ssh/your-key.pem
    PowerShellon your laptop · key permissions
    icacls C:\path\to\your-key.pem /inheritance:r /grant:r "$($env:USERNAME):(R)"
  3. Copy the surfaces to the laptop

    You upload from the laptop, not from the box, so the five files have to be on the laptop first. Run this in a second window, not the one holding the tunnel. It takes seconds.

    Git Bashon your laptop · run it from the folder you want the files in
    cd ~/Desktop
mkdir -p surfaces && cd surfaces
scp -i ~/.ssh/your-key.pem ubuntu@16.58.201.228:/home/ubuntu/Certonomous/demo-surfaces/* ./

    PowerShell runs the same scp line with a Windows key path, but Git Bash is the one to use: it is the same shell you use for the tunnel and the backup bundle, so there is one less thing to get wrong on the day.

  4. Switch the keepalive on before you roll

    This one is easy to forget and it ends the shoot if you do. A timer on the box powers it off after thirty idle minutes, and the control room does not count as activity. Talking to camera between acts looks exactly like an idle box. Verified today.

    Run this once in the SSH window before filming. It expires on its own, so forgetting to switch it off costs nothing.

    In the SSH windowon the lab box
    cd /home/ubuntu/Certonomous
bash scripts/filming_keepalive.sh on 6      # six hours, then it lapses by itself
bash scripts/filming_keepalive.sh status    # check it took

    You should see Keep-alive ON for 6h and the time it lapses.

  5. Restart the control room before you start

    A restart is what loads the current act code, and one act does not run correctly through a server that has been up since before today's fix. Do this before you roll, never between takes of the same act.

    In the SSH windowon the lab box · safe to run twice
    cd /home/ubuntu/Certonomous
bash scripts/demo_servers.sh

    Then confirm both are answering. Both lines should print 200. This one is safe to show on camera.

    In the SSH windowon the lab box · safe on camera
    curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8765/
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/
  6. Never restart while an act is running

    Found the hard way in rehearsal. Restarting the server mid-mission kills that mission on the spot and puts "Mission interrupted by a service restart" on screen. The race runs about three minutes, so it is the one most exposed. Restart between acts or not at all.

  7. Keep the box otherwise quiet

    Every act opens by reading the live state of the machine. On a quiet box that line reads YES and says the full fan-out can run in one wave. With other jobs running it reads NO and drops to capacity 1, which looks like a resource failure on camera even though nothing is wrong. Verified today: with nothing else running it reads YES at capacity 14.

    quiet box, what you want

    Compute audit, YES

    capacity 14, 14 of 16 cores free, 0 other jobs. Full fan-out can run in one wave.

    busy box, avoid

    Compute audit, NO

    capacity 1, cores held by other jobs. Reads as a resource failure on camera.

  8. The offline backup, if the box or the wifi is gone

    There is a bundle that runs on the laptop with no internet and no lab box. Copy the zip across, extract it, and run it from Git Bash. It needs Python installed with the "Add python.exe to PATH" box ticked, and nothing else. A short start-here note ships inside the zip.

    Git Bashon your laptop · fetch the bundle
    scp -i ~/.ssh/your-key.pem ubuntu@16.58.201.228:/home/ubuntu/Certonomous/dist/certonomous-demo.zip ~/Desktop/
    Git Bashon your laptop · right-click inside the extracted folder, Open Git Bash here
    bash run-demo.sh
    Be straight about what the backup is. It replays four recorded acts and serves the closure and benchmarks pages. It cannot run a live act, and that is not a limitation worth hiding: the live acts genuinely invoke VSPAERO and OpenFOAM, and neither exists on a Windows laptop. The numbers it shows are the numbers those runs measured. Nothing in it is a mock-up.

Two rules that decide which act runs

do this

Attach with the button

The control room has a Load a surface button under the prompt box. It takes STL and OBJ up to 200 MB and parses the file the moment it lands, so a bad file is refused straight away instead of failing halfway through a mesh. The button says which body. The prompt says what question.

never do this

Never type the filename into the prompt

Naming a file in the prompt text changes which act runs. Type the race prompt with a filename in it and you get a generic geometry study instead of the race. Nothing on screen tells you why.

One surface, one launch. An attached surface is consumed by the launch it was attached to, and the panel visibly resets afterwards. If you want a second act on the same body, attach it again. This matters because an attached surface reads as "run it on this body": leaving one attached would turn the next act into a generic geometry study on the wrong shape.
Four acts keep their own identity with a surface attached. The airliner optimization, the Monte Carlo race, the valve study and the shape optimization all stay themselves and simply run on your body. Everything else with a file attached becomes a geometry study.

4 · The adjoint act, beat by beat

This is the one act where the clock on the wall and the clock on screen are different numbers. It computes in under a second and then plays for about 47 seconds. Time your narration against the playback, not the run. Plan three quarters of a minute, not one second.

28.3%
drag reduction at matched lift
After 47 major iterations. Measured against our own baseline at the same lift.
1.71%
worst gradient check
Against a 5% standard, so it clears by a factor of 2.9. Best check 0.00145%.
105
design variables
96 shape control points, 7 twist stations, 2 flow-state.
Partial
how it stopped
A 60-minute wall clock ran out. No convergence statement printed.

What appears on screen, in order

  • The baseline wing.
  • The finite-difference verification, all six groups. Worst 1.71%, best 0.00145%, every geometric constraint at machine precision. Gate passes.
  • The adjoint gradient painted on the wing skin, about 18 seconds in. This is the shot. It is the real recorded gradient, mapped onto the surface through the geometry's own map.
  • The wing morphing across 48 frames, about 20 to 24 seconds, with the drag trace descending step for step alongside it.
  • A root close-up of the same morph, about 27 to 32 seconds, where the section change is legible: the baseline is a slim near-symmetric section, the final is visibly fatter and cambered.
  • 28.3% drag reduction at matched lift, after 47 major iterations.
  • A separate table, how the optimization stopped. A 60-minute wall clock, no convergence statement printed, both first-order measures about an order of magnitude above tolerance, status Partial.
Everything on screen is at true scale. The act cannot exaggerate, because the scaling code was removed outright. The shapes were rebuilt by replaying the optimizer's own recorded design variables through the same map it used, verified linear to 7.4e-15. It is a replay of what the optimizer did, not a model of it. Real magnitudes if anyone asks: maximum displacement 185.9 mm, which is 3.72% of the 5 m root chord, and the biggest twist change is -3.03 degrees at the outboard station.
If someone says the change looks subtle, this is the better answer. The act states that it could have amplified the shape by at most x1.995 before the wing passes through itself, because this optimizer drove the wing onto its own thickness constraint: thinnest station 0.4988 against a limit of 0.5. It declined to amplify at all. That is a stronger answer than a bigger picture would have been.
SAY THIS
"A real discrete adjoint, finite-difference verified, and we stopped it on a clock before it converged, so that 28% is a partial result."

5 · What not to say

Short and blunt. The acts already put the honest framing on their own faces, so the safest move in every case is to let the act run and say less.

do not say

Do not call the cylinder shape-optimization act an adjoint

That one is a surrogate-gradient study, a differentiable model fitted to four solver runs. Real design optimization, genuinely good, but a technical audience knows the difference and the distinction is not worth losing. Only the wing act is a genuine adjoint.

do not say

Do not say the adjoint converged, or that 28.3% is validated

It did not converge. It was stopped by a 60-minute clock with no convergence statement printed. The 28.3% is measured against our own baseline at the same lift, not against a wind tunnel.

do not say

Do not claim a rank in the closure challenge

The entry is unsubmitted and we hold no rank. The page carries an UNSUBMITTED banner and says so in plain text. It states it would sit third of five if submitted, and that it currently sits nowhere. Say that, not a rank.

do not type

Do not type the retired ONERA M6 prompt

That act was withdrawn from the filmed sequence. The old prompt no longer runs it: it falls through to a generic geometry study that has never been timed or rehearsed. An untimed run live on camera is the one thing you do not want. Its honest unconverged result stays on the permanent record, which is where it belongs.

The standing line, if you are ever unsure. The demo may withhold method. It may never misstate a result. When those two pull against each other, say less and stay true, never the reverse.
